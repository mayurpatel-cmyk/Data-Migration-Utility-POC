How to Use the Migration Engine

Our platform provides two primary pathways for data migration: Direct API Sync (System-to-System) and CSV/Excel Upload. Follow these core steps to execute a successful migration.

1
Connect Your Systems

Navigate to the Connections tab. Authenticate both your Source (where data comes from) and Target (where data goes) CRMs using OAuth 2.0. You must have Admin privileges in both systems.

2
Select a Migration Pathway

Choose between direct API integration or uploading a static CSV/Excel file. API integration allows you to write SQL/JSON queries to filter live data before moving it.

3
Map Your Fields

Use the mapping interface to link Source columns to Target fields. Use the Auto-Map feature to save time. Ensure all fields marked with a red "Required" badge are mapped.

4
Validate & Execute

Run the validation sequence. The engine will check your data against the Target CRM's strict schema rules without actually writing the data. Fix any errors in the grid, then click Run Job to push the live data.

5
Fix & Re-Validate (No Re-Upload Needed)

If rows are flagged, correct them directly in the results grid and click Re-validate — the engine re-checks only the corrected rows against your original upload session. You don't need to start over from a fresh file upload.

Data Preparation Best Practices

Ensure your CSV or Excel files are properly formatted before uploading to prevent validation errors and data corruption.

  • Date & Time Formats

    Use standard ISO 8601 formats. For dates, use YYYY-MM-DD (e.g., 2024-12-31). For DateTimes, use YYYY-MM-DDTHH:MM:SSZ. Warning: Excel often silently changes your date formats; always double-check before exporting to CSV.

  • Boolean (Checkbox) Fields

    Use explicit true/false values. Accepted formats are usually TRUE/FALSE, 1/0, or Yes/No.

  • Picklists & Multi-Selects

    Picklist values are case-sensitive and must exactly match the CRM's active options. For multi-select picklists, separate your values with a semicolon (;) and no spaces (e.g., Apple;Banana;Orange).

  • Excel 15-Digit Limit (IDs)

    Excel will automatically round numbers longer than 15 digits (like Salesforce 18-digit IDs), corrupting them. To prevent this, format the ID column as Text in Excel before pasting your IDs.

  • "Null" and Empty Values

    Don't worry if your Excel export contains words like #N/A, null, NaN, or <na>. Our Payload Builder automatically detects and scrubs these out so the literal word "null" isn't pushed to your CRM.

  • Duplicate Key Values in One File

    If your file has two or more rows with the same value in your Upsert/Update key field, only the last occurrence is sent — earlier duplicates are skipped and reported with a reason in your audit log, rather than being sent and letting the CRM's own (non-deterministic) duplicate handling decide. Dedupe your source data first if this isn't the behavior you want.

Troubleshooting & FAQ

Common issues encountered during migration and how to resolve them.

You are likely using Insert mode, and the CRM has identified that this record already exists (usually based on Email, Domain, or Name). To update existing records instead of failing, switch your migration mode to Upsert and map an External ID or Email as your Upsert Key.

Every CRM has strict rules for creating objects. For example, Salesforce requires a LastName to create a Contact. If you do not map a column from your CSV to that required CRM field, the system will block the migration to prevent corrupt data.

Every CRM has API rate limits (e.g., Zendesk only allows a certain number of requests per minute). Our Data Engine monitors this in real-time. If you hit a rate limit, the engine will safely pause itself (usually for 10 to 30 seconds) and automatically resume. No data is lost; just let it run!

If you are pushing hundreds of thousands of records, the target CRM's API might throttle the connection. Go to the "Review Final Migration Plan" step and lower the Record Size (Batch Size). This forces the engine to send smaller, more digestible chunks of data to the CRM.

When you map a lookup field (like AccountId), an extra dropdown will appear asking for the Parent Ext ID. If your CSV has the actual CRM ID of the Account, select Id. If your CSV has a custom identifier (like a Legacy Database ID), select that custom field so the engine can automatically resolve the relationship.

Update mode is only supposed to touch existing records, never create new ones. Some CRM APIs will auto-create a record anyway if no match is found on your key field. SureShift detects this and automatically reverts (deletes/archives) any record the CRM auto-created under Update mode, then reports that row as skipped with the reason. You won't see orphaned records left behind — but you will see a skip reason in your audit report, which is worth reviewing.

Update and Upsert modes require a mapped External ID / dedupe key field before any data is sent — without one, the CRM has no reliable way to match rows to existing records. If that field isn't configured, the engine fails the entire batch up front (before making any API calls) rather than guessing at a match. Go back to the mapping step and set a Target External ID Field.

Fix the flagged rows directly in the results grid and click Re-validate; only the corrected rows are re-checked against the same session, and your original valid rows aren't touched. Staged sessions do expire after a period of inactivity, though — if you see "Staging session expired," you'll need to re-upload.

Technical Specifications

The migration engine is built to handle massive datasets securely without crashing your browser. It utilizes WebSockets for real-time streaming and asynchronous batch processing.

Module Specification & Capability
Architecture Angular Frontend, Python/Node.js Data Engine, WebSocket Streaming.
Security & Auth Stateless OAuth 2.0 processing over encrypted TLS. CRM credentials are stored (encrypted at rest) to enable silent token refresh across sessions. Validation runs are staged server-side per session to support pause/fix/re-validate without re-uploading; staging data and generated audit reports (PDF/CSV) are retained per your data-retention policy, not streamed-and-discarded.
Batch Limits Auto-chunking limits apply per CRM. Salesforce (5,000 default batch, configurable up to the platform's 10,000 ceiling), Zendesk (100 max), HubSpot (100 max), Zoho (100 max per batch; COQL query results additionally capped at 200 rows per request).
Multi-Object Migrations When migrating several related objects in one job (e.g., Accounts + Contacts), the engine automatically orders them by lookup/reference dependency — parent objects before the children that reference them — so relationship fields resolve correctly without you having to sequence the jobs manually. Circular references are handled with a deferred patch pass.
Session Resilience If your CRM access token expires mid-migration, the engine silently refreshes it and retries the in-flight request — a running migration will not stop or fail just because a token expired.
Data Validation Module Enforces strict CRM schema rules prior to migration. It automatically validates all data types:
  • Strings: Enforces maximum character length limits.
  • Numbers/Currency: Blocks text input and verifies precision constraints.
  • Booleans: Normalizes inputs to valid CRM boolean states (true/false).
  • Dates/DateTimes: Validates and auto-converts to ISO 8601 standard formats.
  • Picklists: Ensures values are case-sensitive exact matches against active CRM picklist options.
  • Multi-Picklists: Validates semicolon-delimited values against allowed options.
  • References/Lookups: Verifies relational parent keys and External ID resolutions.
Error Handling Row-level transaction rollbacks. One failed row will not fail the entire batch. Generates downloadable audit logs for success and failures.

Salesforce Configuration & Rules

Authentication Requirement: You can log in instantly using our pre-approved Global Auth Client. However, if your Salesforce org restricts third-party integrations, you must configure a private Connected App.
Salesforce Data Rules
  • State & Country Picklists: The engine automatically converts full country and state names (e.g., "United States of America") into standard ISO Alpha-2 codes (e.g., "US") for you.
  • Salesforce IDs: Any mapped Salesforce ID must be strictly alphanumeric and exactly 15 or 18 characters long.
  • Website URLs: The engine will automatically prepend https:// to any website fields if it is missing.
  • Dependent Picklists: The engine automatically respects picklist dependencies. If you map a dependent field, its value must be valid for the parent (Controller) field's value.
  • Multi-Currency Orgs: If your Salesforce Org uses multiple currencies, you must map the CurrencyIsoCode column whenever mapping currency fields, or the row will fail.
  • Sandbox vs. Production: When connecting a Salesforce org, choose Production or Sandbox up front — this determines whether the engine authenticates against login.salesforce.com or test.salesforce.com. Connecting to the wrong environment is the most common cause of an org "not showing the objects I expect."
  • File & Attachment Migration: Migrating record attachments (legacy Attachments and modern Files) is currently supported Salesforce → Salesforce only. Moving files into or out of Zoho, Zendesk, or HubSpot is not yet supported — only the record data itself migrates for those CRMs.
Private Connected App Setup (If Required)
1

Log into Salesforce as a System Administrator. Go to Setup > App Manager > New Connected App.

2

Enable OAuth Settings. Set the Callback URL to this application's redirect URI (e.g., https://your-app.com/oauth/callback).

3

Select required OAuth Scopes: Manage user data via APIs (api), Perform requests at any time (refresh_token, offline_access).

Zendesk Configuration & Rules

Authentication Requirement: You can authorize via our Global Auth Client (OAuth). Alternatively, if you require a service account integration, you can use a generated API Token from your Zendesk Admin Center.
Zendesk Data Rules
  • Ticket Statuses: Must exactly match: new, open, pending, hold, solved, or closed.
  • Ticket Priorities: Must exactly match: low, normal, high, or urgent.
  • Zendesk Tags: Tags cannot contain special characters (like @, #, !). The engine will automatically convert commas and semicolons into spaces.
  • Lookup IDs: Any mapped Zendesk ID must be purely numeric (no letters).
API Token Setup (Alternative)
1

Identify your subdomain. If your URL is https://mycompany.zendesk.com, your subdomain is mycompany.

2

Log in to Zendesk Admin Center. Navigate to Apps and integrations > APIs > Zendesk API.

3

Enable Token Access. Create a new API token, copy it immediately, and save it in your Migration Engine connection settings.

HubSpot Configuration & Rules

Authentication Requirement: Most users can authorize using our Global Auth Client (Public App). Since HubSpot has deprecated API Keys, strict environments will need to configure a Private App.
HubSpot Data Rules
  • String Limits: HubSpot strictly limits standard text properties to 65,536 characters.
  • Emails: Email fields are strictly validated against a regex pattern to prevent the HubSpot API from rejecting the entire batch.
  • Multiple Checkboxes: If mapping to a multiple checkbox property, use semicolons (;) to separate your values.
  • Associations Are Not Auto-Migrated: Unlike Salesforce/Zoho lookups, HubSpot links objects (e.g., Contact ↔ Company, Deal ↔ Contact) through a separate Associations API rather than a property on the record. Reference/lookup fields mapped to a HubSpot target are currently not written automatically — plan a manual or custom association pass after the object migration completes.
Private App Setup (If Required)
1

In your HubSpot account, click the Settings icon in the main navigation bar.

2

Go to Integrations > Private Apps and click Create a private app.

3

Under the Scopes tab, grant read and write permissions for the objects you intend to migrate (e.g., crm.objects.contacts.read, crm.objects.contacts.write).

Zoho CRM Configuration & Rules

Authentication Requirement: You can seamlessly log in using our Global Auth Client. If your Zoho CRM is heavily customized or siloed, you will need to register a private application in the Zoho API Console.
Zoho Data Rules
  • Zoho IDs: Native Zoho IDs (like OwnerId or ParentId) are extremely strict. They must be purely numeric and exactly 18 or 19 digits long (e.g., 4150868000004938001). Excel often breaks these, so format your ID column as Text before saving.
  • Read-Only Fields: Auto-Number and Formula fields cannot be mapped. The engine will block data mapped to these fields.
Private API Console Setup (If Required)
1

Identify your Data Center Region. Check your Zoho URL (e.g., zoho.com is US, zoho.eu is Europe, zoho.in is India).

2

Go to the Zoho API Console (api-console.zoho.com) and click Add Client > Server-based Applications.

3

Ensure the required scope ZohoCRM.modules.ALL is approved when authorizing the application connection.
